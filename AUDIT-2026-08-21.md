## 2. Производительность: что реально остаётся

1. **Шрифты — самая тяжёлая статья первой загрузки.** `app/globals.css` тянет одним
   `@import` с Google Fonts **10 семейств × 4–7 начертаний** (~40+ файлов). CSS-`@import`
   — блокирующая цепочка: globals.css → fonts.googleapis.com → fonts.gstatic.com.
   Предложение: всегда грузить только Manrope (через `<link rel="preload">` + preconnect),
   остальные 9 семейств подгружать по факту выбора в настройках (инъекция `<link>` при
   смене `fontFamily`). Оценка выигрыша: −200…400 КБ и заметно быстрее первый кадр.
2. **`/api/letters/public` запрашивается при каждой полной загрузке** (дважды из
   `OnboardingModal`, который живёт в корневом layout), хотя нужен только для текста
   welcome-окна. Предложение: кэш в sessionStorage на 10–15 минут.
3. **Контекст настроек перерисовывает всё приложение.** Любое движение ползунка
   (радиусы, масштаб шрифта, цвет) → новый объект `settings` → ререндер всех
   потребителей `useSettings` (шапка, оба меню, страницы). Среднесрочное решение —
   разделить контекст на «значение» и «действия» + подписка через селектор
   (`useSyncExternalStore`). Это рефакторинг, делать без отдельного согласования не буду.
4. **Дев-режим ≠ прод.** Ваши логи — из `next dev` (HMR-пересборки по 0.5–4 с — норма).
   Ощущение «в разы медленнее» почти наверняка усилено dev-режимом + старой сборкой.

## 6. Второй заход (21.08.2026, вечером): прогресс онбординга — в БД

Повод: «если закрыть браузер и войти обратно, гид пропадает, а я остаюсь
зареганным». Причина была в устройстве: номер шага лежал в sessionStorage
(умирает вместе с вкладкой), а `tour_done` ставился уже после 11 шагов — до
двух финальных окон. Плюс по требованию владельца введено правило «онбординг
не закончен — анкета скрыта».

**Новая модель (миграция `supabase/update/65-tour-progress-db.sql`):**

- `user_settings.tour_step int 0..12`: 0–10 — шаги гида, 11 — «Внешний вид»,
  12 — «Заполнить профиль»;
- `tour_done` = «пройдено ВСЁ, включая анкету»; ставится только в
  `finishOnboarding` (после отправки анкеты);
- пока `tour_done = false` — каждый заход открывает онбординг на сохранённом
  этапе, с любого устройства (`OnboardingModal` → `onboardingStageToStep`,
  `FirstTour` стартует с `settings.tourStep`);
- RLS «profiles public read»: личная анкета (`personal-<uuid>`) видна другим
  только при `tour_done = true` владельца; сам владелец и админы видят всегда;
- дедушкин бэкфилл: все существующие пользователи без строки `user_settings`
  получают её с `tour_done = true` — ничьи анкеты из каталога не пропадут;
- гость — вне правила: нет аккаунта, нет гида, нет блокировок;
- локальная метка `daymohk-tour-<id>` и sessionStorage-шаг удалены из логики
  решений — истина только в базе.

**ВАЖНО для проверки у себя:** применяется в два шага —
1) `Supabase → SQL Editor` → выполнить `supabase/update/65-tour-progress-db.sql`;
2) сбросить свой тестовый аккаунт (см. ниже) и почистить site data браузера.

```sql
-- сброс тестового аккаунта, чтобы увидеть гид заново:
update public.user_settings
set tour_done = false, tour_step = 0
where user_id = '<ваш uuid>';
```
