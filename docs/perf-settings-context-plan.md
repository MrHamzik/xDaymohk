# План: контекст настроек и перерисовки (обсуждение)

Статус: **предложение, ничего не применено**. Согласовано подготовить план
(ответ на вопрос №3 аудита от 21.08.2026).

## Проблема

`SettingsProvider` держит все настройки одним объектом в одном React-контексте.
Объект пересоздаётся при каждой правке, а `useSettings()` стоят в десятках
компонентов: шапка, оба меню, нижняя панель, страницы каталога/заданий/анкет.

Следствие: движение любого ползунка (радиус, масштаб шрифта, цвет темы,
«сила градиента») — это:

1. `normalizeSettings` по всем ~40 полям (включая пересборку массивов);
2. `applyThemeColors` — запись ~30 CSS-переменных в `<html>`;
3. перерисовка **всех** потребителей контекста, даже тех, кому изменённое
   поле безразлично (карта не обязана перерисовываться от смены радиуса).

После троттлинга ползунков (один апдейт на кадр) роняющего «Maximum update
depth» больше нет, но перерисовка всего дерева на каждый кадр перетаскивания —
главный оставшийся тормоз на тяжёлых страницах (карта, каталог).

## Варианты

### Вариант 1 (лёгкий): мемоизация потребителей
Обернуть тяжёлые листовые компоненты (списки каталога, карточки, карту) в
`React.memo` — они получают настройки пропсами/селекторами, а не контекстом.
- Плюс: точечно, без смены архитектуры, можно делать по одному файлу.
- Минус: не лечит причину (потребители контекста всё равно перерисуются),
  помогает только там, где мемоизируем; легко забыть на новых компонентах.

### Вариант 2 (средний): разделить контексты «значение» / «действия»
`SettingsUpdateContext` (стабильные `update`/`reset`) отдельно от
`SettingsValueContext` (сам объект). Плюс вынести редко меняющиеся куски
(`notificationPrefs`, `hiddenMenu`, `quickWidgets`) в отдельный контекст.
- Плюс: заметно меньше перерисовок на «холодных» потребителях; правка
  механическая, поведение не меняется; тесты существующие остаются валидны.
- Минус: половина выигрыша — `themeId`/цвета всё ещё в общем объекте.

### Вариант 3 (лучший, индустриальный): стор + подписка селекторами
Перевести настройки на `useSyncExternalStore` (паттерн zustand-redux без
новых зависимостей, либо zustand ~1 КБ): компонент подписывается на
`useSetting((s) => s.radiusScale)` и перерисовывается только при изменении
своего поля. Запись в БД/localStorage — как сейчас, дебаунс сохраняется.
- Плюс: перерисовка ровно тех, кому поле нужно; ползунки перестают трогать
  карту и каталог; это стандартный, проверенный подход (Redux/Zustand/Jotai).
- Минус: самая большая правка (все вызовы `useSettings()`), нужен этапный
  план и защита регрессий тестами; делать за один присест нельзя.

## Рекомендация

Этап 1 — вариант 2 (механически, безопасно, быстрый выигрыш).
Этап 2 — вариант 3 для горячих полей (тема, типографика, радиус), когда
этап 1 обкатастся. Вариант 1 использовать попутно для листовых карточек.

## Смежные шаги (уже сделано 21.08.2026)

- Троттлинг слайдера «Сила градиента» — последний нетроттлированный input
  настроек (класс ошибки «Maximum update depth exceeded»).
- Шрифты: Manrope в `<head>`, остальные 8 семейств лениво (−1 блокирующий
  @import, −порядка 200–400 КБ стилей и файлов шрифтов на первой загрузке).
- Кэш `/api/letters/public` в sessionStorage на 10 минут (−2 запроса на
  каждую полную загрузку страницы).

## Как проверить эффект после этапа 1

1. `npm run build && npm start`, открыть /catalog.
2. React DevTools Profiler: перетащить «Радиус» в настройках — в профиле
   должны остаться только компоненты, читающие тему, а не всё дерево.
3. До/после сравнить счётчик ререндеров Navbar (он читает только язык/тему).
